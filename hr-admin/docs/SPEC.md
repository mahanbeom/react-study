# SPEC — HR 대시보드/관리자 사이트

## 무엇을

React + Vite 기반 HR 어드민 사이트. 백엔드 없이 mock API(MSW)로 실무와 동일한
fetch 구조를 연습한다.

### 기술 스택

- React + Vite + TypeScript (6.x 고정)
- react-router v7 (라이브러리 모드)
- TanStack Query — 서버 상태
- react-hook-form + zod — 폼/검증
- recharts — 차트
- MSW — mock API
- Tailwind CSS v4 — 스타일링
- 공통 설정: `@mahanbeom/kit` (ESLint/Prettier/TypeScript)

### 기능 범위 (구현 순서)

1. **레이아웃/라우팅 뼈대** — 사이드바 + 헤더 레이아웃, 전체 라우트 placeholder
2. **직원 목록 테이블** — 검색 / 필터(부서·상태) / 페이지네이션
3. **직원 상세/등록/수정 폼** — RHF + zod 검증, 생성/수정/삭제 mutation
4. **대시보드 홈** — 인원 현황 카드, 입퇴사 추이 차트
5. **휴가 워크플로우** — 신청 → 대기 → 승인/반려 상태 전이
6. **로그인 + 권한** — 관리자/일반 역할별 화면 분기

## 왜

- 실무 어드민의 표준 구조(라우팅, 서버 상태, 폼, 권한)를 한 프로젝트에서 연습
- mock API 기반이지만 fetch 계층은 실제 백엔드가 붙어도 그대로 쓸 수 있는 형태로 유지

## 아키텍처 규칙

```
src/
  app/       # 도메인 인지: 라우터, 프로바이더, 레이아웃 조립, 페이지
  ui/        # ★ 도메인 무관 재사용 UI — 추후 별도 패키지로 분리 대상
  features/  # 도메인별: employees, dashboard, leave, auth
  lib/       # api client 등 공용 유틸
  mocks/     # MSW 핸들러
```

- **UI 격리 규칙**: `src/ui`는 `app`/`features`/`lib`/`mocks`를 import하지 않는다.
  도메인 데이터(메뉴 항목, 컬럼 정의 등)는 전부 props로 주입한다.
  react-router 등 범용 라이브러리 의존은 허용(패키지 분리 시 peer dependency).
- 설정 변경은 프로젝트가 아니라 kit 저장소에서 한다 (프로젝트 고유 규칙만 예외).

## 완료 기준

- 각 단계: `pnpm lint` + `tsc` 통과, dev 서버에서 실제 구동 확인 후 커밋
- 테스트 가능한 로직(필터링, 상태 전이, zod 스키마 등)은 테스트 선행(TDD)
- 최종: 6단계 전부 동작 + 관리자/일반 계정으로 로그인해 권한 분기 확인

---

# SPEC v2 — ESS/MSS 확장

v1(1~8단계) 완료 후 확장. 현재 앱은 ADMIN 관점 단일 화면이다 — 로그인 계정과
직원 데이터가 무관해서 "내 휴가"가 불가능하고, 권한은 역할 2종(admin/member)의
화면 분기뿐이다. v2는 이를 **셀프서비스(ESS) / 매니저(MSS) / 관리자(ADMIN)**
3관점 구조로 확장한다.

## 무엇을 (범위: 핵심 축만)

급여·근태·평가는 v3 이후로 미룬다. v2는 다음 네 덩어리만 다룬다.

### A. 계정↔직원 연결 (기반)

- `AuthUser`에 `employeeId: string | null` 추가. member 계정은 직원과 1:1 연결,
  admin 계정은 직원이 아닐 수 있다(null 허용).
- 데모 계정 시드를 실제 직원 시드와 연결한다.

### B. 조직 계층 — 부서장 모델 (기반)

- 부서를 문자열 union에서 **엔티티로 승격**: `Department { id, name,
managerEmployeeId }`. 부서마다 부서장(직원) 1명을 지정한다.
- **역할(role)은 admin/member 2종 유지.** "부서장 여부"는 role이 아니라
  계정→직원→부서.managerEmployeeId **관계에서 파생**한다(`isManager`).
  이중 소스(role에 manager 추가)를 만들지 않는 것이 v2의 핵심 학습 포인트:
  권한이 "역할 기반"에서 "관계 기반"으로 확장되는 구조.

### C. 연차 잔여 관리 (기반)

- **고정 부여**: 전 직원 연 15일. `LeaveBalance { employeeId, year, granted,
used }` — 잔여는 파생값(granted − used).
- 차감·복원 규칙: **승인 시 차감**(annual = 일수, half = 0.5일),
  **반려·취소 시 복원**. sick(병가)은 연차 차감 대상이 아니다.
- 일수 계산은 **달력일 기준으로 단순화**(주말·공휴일 제외 없음 — 스펙에 명시된
  의도적 단순화. 영업일 계산은 확장 아이디어로 남김).
- 부여-차감-복원 정합성 로직은 순수 함수로 분리해 TDD.
- 신청 시 잔여 초과 검증: 클라이언트(zod)와 mock 서버 양쪽에서 같은 규칙 공유
  (v1 규칙 유지).

### D. 화면 — ESS / MSS / ADMIN 분리

- **ESS (모든 로그인 사용자)**
  - 내 정보: 연결된 직원 정보 + 올해 연차 현황(부여/사용/잔여) 조회
  - 내 휴가: 본인 휴가 목록 + **본인 명의 신청**(직원 드롭다운 없음)
- **MSS (isManager인 사용자)**
  - 팀 결재함: 자기 부서원의 pending 휴가 목록 → 승인/반려.
    다른 부서 건은 목록에 없고, API도 관계 검증으로 거부한다.
- **ADMIN (admin 역할)**
  - 기존 화면 유지: 직원 CRUD, 전체 휴가 목록, 전 부서 결재 가능.
  - 기존 대리 신청(직원 드롭다운 선택)은 admin 전용으로 유지.

## 왜

- 실무 HR 시스템의 표준인 3관점(ESS/MSS/ADMIN) 구조와, 권한이 역할→관계
  기반으로 확장되는 패턴을 연습
- 부여-차감-복원처럼 정합성이 중요한 도메인 로직을 순수 함수 TDD로 다루는 연습

## 구현 순서 (v1에 이어 9~12단계)

9. **계정↔직원 연결 + 부서 엔티티** — 데이터 모델 기반 작업.
   AuthUser.employeeId, Department 엔티티, isManager 파생, 시드 재구성
10. **연차 잔여** — LeaveBalance + 부여/차감/복원 순수 함수(TDD) +
    승인/반려 흐름에 연결 + 신청 시 잔여 검증
11. **ESS** — 내 정보 / 내 휴가 / 본인 명의 신청 전환
12. **MSS** — 팀 결재함(관계 기반 권한, 서버 측 검증 포함)

각 단계는 v1과 동일한 관례를 따른다: Plan mode 승인 → TDD → 브라우저 실증 →
커밋, 계획은 `docs/plans/N-*.md`에 기록.

## 완료 기준 (v2)

- 기존 테스트 91개 포함 전체 테스트 통과, lint + `tsc -b` 클린
- 계정 3종 시나리오를 브라우저에서 실증:
  1. **일반 member**: 내 휴가 신청 → 잔여 차감 없음(pending) → 팀 결재함 접근 불가
  2. **부서장 member**(isManager): 팀 결재함에서 자기 부서 건만 보임 →
     승인 시 신청자 잔여 차감 확인
  3. **admin**: 전 부서 결재 + 대리 신청 + 직원 CRUD 유지
- 잔여 정합성: 승인→차감, 반려→복원이 새로고침(시드 리셋 아닌 세션 내)에서도
  일관됨을 확인
