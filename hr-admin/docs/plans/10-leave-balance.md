# 10단계: 연차 잔여 관리

SPEC v2 C절. 잔여 개념이 없어 휴가를 무제한 신청할 수 있던 것을 해소한다.
전 직원 연 15일 고정 부여 기준.

## 설계 결정

1. **신청 시 예약 모델** — 잔여 = `granted(15) − used(승인분) − reserved(대기분)`.
   신청 즉시 예약되므로 중복 신청으로 잔여가 음수가 될 수 없고, 반려되면 예약분이
   사라져 "복원"이 자동으로 이뤄진다. 실무 HR 시스템 표준.
2. **파생 계산** — used/reserved를 저장하지 않고 휴가 신청 목록에서 매번 계산한다.
   balanceDb 없음, `setup.ts` 리셋 체인 무변경. 차감/복원 누락 버그가 원천 불가능.
3. **decision 경로 완전 무변경** — 승인은 reserved→used 이동(잔여 불변),
   반려는 reserved 소멸(잔여 복귀). `decide`, PATCH 핸들러, 8단계 낙관적 업데이트를
   한 줄도 고치지 않았다. 파생 모델의 핵심 이점.
4. **순수 함수는 `features/leave/balance.ts`** — 클라이언트/서버 공유이므로 mocks가 아닌
   features. (의존 방향은 mocks → features. 반대로 두면 프로덕션 번들에 mock이 딸려온다.)
   `exceedsRemaining`이 `LeaveBalance`를 받는 이유: 클라이언트는 신청 목록 전체가 아니라
   GET 응답만 갖고 있어서, 이렇게 해야 판정 로직이 실제로 공유된다.
5. **zod 스키마 팩토리 미사용** — 잔여 검증은 스키마 밖 서버 체크(`isEmailTaken` 선례).
   스키마를 팩토리로 바꿨다면 기존 스키마 테스트 7개가 전부 시그니처 변경 대상이 됐다.
6. **leaveKeys에 balance 편입** — `leaveKeys.all` 하위라서 기존 뮤테이션의
   `invalidateQueries(leaveKeys.all)`가 잔여까지 갱신한다 → `mutations.ts` 무수정.
   `onMutate`의 `cancelQueries`는 `lists()`만 대상이라 잔여는 낙관적 경로와 안 엮인다
   ("가시적 전이가 있는 곳만 낙관적 업데이트" 8단계 결정과 일치).
7. **반차는 시작일=종료일 강제** — 기간과 무관하게 0.5일 차감이므로 스키마 규칙 추가.

## 검증 결과

- 테스트 125개(기존 104 + 신규 21) / lint / `tsc -b` 클린
- 브라우저 실증(admin, SPA 내비게이션 — 전체 새로고침은 인메모리 mock DB를 리셋함):
  1. 조우진 상세: 부여 15 / 사용 0.5 / 잔여 14.5 (시드의 승인된 반차 반영)
  2. 30일 연차 신청 → `잔여 연차(14.5일)를 초과합니다`, **POST 요청 자체가 발생하지 않음**
  3. 3일 연차 신청 성공 → 대기 3일, 잔여 14.5 → 11.5 (예약 모델 가시화)
  4. 그 건 승인 → 사용 +3, 대기 0, **잔여 11.5 불변** (reserved→used 이동)
  5. 대기중 반차 반려 → 잔여 14.5 → 15 자동 복원
  6. 반차 이틀 신청 → `반차는 하루만 신청할 수 있습니다`

직원별 부여일수 차등·이월·소멸 정책 / 반차 선택 시 종료일 자동 동기화 /
